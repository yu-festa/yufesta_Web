# Swagger API 연동 검증 — 2026-09-28

현재 로컬 프론트 작업 트리 기준으로 public 33개, admin 37개, 총 70개 API의 호출 함수와 화면·공통 클라이언트 연결을 확인했다. **호출 연결 누락은 없지만, 운영 서버 CORS 설정 때문에 관리자 공연 순서 변경이 차단되어 전체 기능의 운영 정상 동작을 확정할 수 없다.**

## 기준과 검증 범위

- [public Swagger](https://api.yufesta.com/swagger-ui/index.html?urls.primaryName=public#/Auth/getMe), [admin Swagger](https://api.yufesta.com/swagger-ui/index.html?urls.primaryName=admin): 두 페이지 모두 HTTP 200 확인.
- [public OpenAPI](https://api.yufesta.com/v3/api-docs/public), [admin OpenAPI](https://api.yufesta.com/v3/api-docs/admin): 점검 시점에 직접 내려받은 명세 사용. Swagger 설정에서 두 문서가 각각 public/admin 그룹으로 연결되어 있음을 확인.
- API 경로·메서드, 호출부, JSON 요청 28개의 필드와 enum, 응답에서 사용하는 필드와 enum을 프론트 선언 및 화면과 대조했다. 사진 업로드 두 종류는 multipart `file`, JPEG/PNG, 최대 10MB, Content-Type boundary 자동 생성 처리를 확인했다.
- 라이브 검증은 운영 서버의 GET 및 OPTIONS만 사용했다. 실제 신청·등록·신고·수정·삭제·발표는 실행하지 않았다.
- 일반 사용자·STAFF·OWNER 로그인 세션을 사용하지 않았다. 해당 권한의 성공 응답과 저장 결과까지 확인한 것은 아니다.
- 이전 작업에서 추가한 `displayName`, `profileImageUrl` 연동을 포함한 로컬 코드 기준이다. 현재 배포된 프론트에 이 코드가 반영되었는지는 별도 검증하지 않았다.

## 확인된 문제: 공연 순서 변경 PUT 사전 요청 거절

| 항목 | 근거 |
| --- | --- |
| 기능 | 관리자 타임테이블의 `위로` / `아래로` 순서 변경 |
| 명세 및 프론트 요청 | `PUT /api/v1/admin/timetable/order`, JSON `{ "slotIds": [...] }` |
| 호출 함수 | [adminContent.ts](../src/api/adminContent.ts), `reorderTimetableSlots` |
| 화면 연결 | [AdminTimetable.tsx](../src/pages/admin/AdminTimetable.tsx), `move()` |
| 서버가 알린 허용 메서드 | `GET,POST,PATCH,DELETE,OPTIONS` — PUT 없음 |
| 실제 사전 요청 | 위 경로로 OPTIONS, `Access-Control-Request-Method: PUT`, `Access-Control-Request-Headers: content-type,x-xsrf-token` |
| Origin `https://yufesta.com` | HTTP 403, 본문 `Invalid CORS request` |
| Origin `https://www.yufesta.com` | HTTP 403, 본문 `Invalid CORS request` |

현재 배포용 API 설정은 브라우저에서 `https://api.yufesta.com`을 직접 호출한다([apiConfig.ts](../src/utils/apiConfig.ts)). 따라서 브라우저가 실제 PUT 요청 전에 수행하는 사전 요청에서 막힌다. 개발 환경의 동일 출처 프록시나 모의 API 테스트에서는 발견되지 않을 수 있다.

**필요 조치:** 백엔드 CORS 허용 메서드에 `PUT`을 추가하고, 두 운영 프론트 Origin에 대해 해당 OPTIONS 요청이 성공하는지 다시 확인한다. 이후 운영자 테스트 계정으로 순서 변경 후 재조회하여 저장 결과를 확인한다. 프론트에서 요청을 POST로 바꾸는 것은 Swagger 계약과 맞지 않는다.

- 비로그인 상태에서 `auth/me`, `match/applications/me`, `match/results/me`, 관리자 clubs·timetable·match/rounds·match/reports·content-reports 조회 8개는 모두 예상대로 HTTP 401 / `UNAUTHORIZED`를 반환했다.
- `GET /api/v1/auth/csrf`: HTTP 204, XSRF-TOKEN 쿠키 발급 확인. Domain=yufesta.com, Path=/, Secure, SameSite=Lax이며 HttpOnly가 아니어서 기존 프론트 토큰 읽기 방식과 맞는다. 쿠키 값은 기록하지 않았다.
- 공개 조회에서 Origin `https://yufesta.com` 허용과 `Access-Control-Allow-Credentials: true` 확인. `https://www.yufesta.com`도 clubs 조회로 확인했다.
- 두 Origin에서 POST 사전 요청은 HTTP 200이며 `content-type`, `x-xsrf-token`을 허용했다. PUT 사전 요청은 위 문제처럼 거절되었다.

## 연결되어 있으나 API 범위에 따른 제약

- 분실물 단건 상세 API와 원글의 `mine`/작성자 ID가 없다. 상세는 최근 최대 50개 목록에서 찾으며, 본인 글의 사진 관리·해결·삭제 권한은 서버가 최종 확인한다. 오래된 글의 직접 접근과 본인 버튼 구분에는 제약이 있다.
- 비공개 장소용 관리자 목록·상세 API가 없다. 비공개로 저장한 장소는 화면을 떠난 뒤 목록에서 다시 선택할 수 없다.
- 댓글 신고 응답에 원글 `lostItemId`가 없다. 댓글 신고에서 숨김/복구를 하려면 원글 번호를 별도로 입력해야 한다.
- 숨긴 응원·분실물을 모두 조회하는 관리자 API가 없다. 신고 목록이나 직접 입력한 ID로 복구한다.
- 소셜 표시 이름·프로필 사진은 최신 명세와 로컬 코드가 일치한다. 인스타팅 신청 없이도 표시되며, 이름이 비면 기본 이름, 사진이 없거나 로딩에 실패하면 기본 아이콘을 사용한다. 실제 소셜 로그인 세션의 사진 응답은 이번 점검에서 확인하지 않았다.

## 문서 자체의 제약

70개 작업 중 40개는 OpenAPI `responses`에 2xx 성공 응답 코드가 빠져 있다. 일부에는 성공 형태의 `ApiResponse...` 스키마가 400/404 등의 응답 아래 붙어 있다. 연결된 스키마와 프론트 사용 필드는 대조했지만, 그 사실만으로 실제 성공 응답 상태와 본문을 보장할 수 없다.

동아리 사진 업로드는 프론트에서 반환 본문을 사용하지 않고 성공 후 목록을 다시 조회한다. 반환 타입이 `void`인 것은 현재 화면 동작의 연결 누락으로 판단하지 않았다.
