# 인스타팅 QA 실행 플로우

작성일: 2026-09-28. 현재 프론트 구현, 인스타팅 API 계약, 공개 API 캐시 안내를 기준으로 작성했다. 이 문서는 **테스트 절차이며, 아래 항목을 실제 실행해 통과했다는 뜻은 아니다.**

## 1. 실행 순서와 준비

**기본 순서:** 비로그인 진입 → 로그인 → 신청 → 수정 → 취소·재신청 → 마감·매칭 → 발표 → 성공·미매칭 결과 → 다음 회차 재참여·자동 이월 → 최종 회차 종료.

신고·제재는 신청과 매칭 상태를 바꾸므로 기본 흐름을 완료한 뒤 별도 테스트 데이터로 진행한다.

### 테스트 환경

- 테스트용 서버와 회차를 사용한다. 회차 생성·초기화는 현재 관리자 화면에 없으므로 백엔드에서 준비한다.
- 실제 서버 연동 QA에서는 `VITE_PROFILE_PREVIEW`를 비활성화한다. 예시 결과 카드로 실제 결과 검증을 대신하지 않는다.
- 테스트할 프론트 주소, 배포 버전/커밋, API 주소, 테스트 날짜를 기록한다. 루트가 축제 전 랜딩으로 열리면 `/main`에서 시작한다.
- 일반 사용자와 관리자는 별도 브라우저 프로필로 접속한다. 여러 사용자도 세션이 섞이지 않도록 분리한다.
- 기준 브라우저는 모바일 Safari와 Android Chrome, 관리자 검증은 데스크톱 Chrome으로 잡는다.

### 필요한 계정과 데이터

| 구분 | 준비할 상태 | 용도 |
| --- | --- | --- |
| 비로그인 | 쿠키 없는 세션 | 로그인 유도, 접근 제한 |
| 사용자 A | Google 로그인, 신규 신청 가능 | 신청·수정·결과·재참여 |
| 사용자 B | Kakao 로그인, 신규 신청 가능 | 다른 계정 분리, 중복 ID, 매칭 상대 |
| 사용자 C | 미매칭 결과를 확인할 테스트 사용자 | 미매칭·자동 이월 |
| 사용자 D | 해당 회차에 신청하지 않은 사용자 | 결과·수정 화면 직접 접근 |
| STAFF | 운영자 | 회차 운영, 신고 검토, 발표 권한 제한 |
| OWNER | 총괄 운영자 | 결과 발표 |

- A/B의 매칭 성공과 C의 미매칭은 백엔드에서 검증 가능한 테스트 데이터로 준비한다. 실제 배치를 검증할 때는 관리자 배치 결과와 사용자 결과를 대조한다. 단순히 남녀 인원수만으로 특정 계정의 결과를 확정하지 않는다.
- 한 명의 상대 카드, 복수 상대 카드, 선택 항목이 비어 있는 상대, 신고 후 카드가 전부 사라진 상태를 각각 재현할 수 있게 준비한다. 필요하면 별도 데이터 세트로 실행한다.
- 1차와 2차 회차를 준비한다. 시각은 한국 시간이며 `openAt < closeAt`, `publishAt = closeAt + 10분`을 만족해야 한다. 수동 접수 시작 후에도 현재 서버 시각이 접수 구간에 들어와 있어야 신청할 수 있다.
- 현재 회차에서 선택 가능한 공연과 다음 회차에서는 더 이상 선택할 수 없는 공연을 준비한다.
- 예시 신청값: 닉네임 `축제친구`, 인스타 ID `qa_festa_a`, 성별 1개, 나이대 `22-24`, 태그 `MUSIC`·`CAFE`, 소개 `같이 공연 봐요`. 실제 저장에는 테스트용 ID를 사용한다.

### 기록 방법

각 행의 결과에 `통과 / 실패 / 보류`를 적는다. 미실행은 `—`로 둔다. 데이터나 권한 부족으로 재현하지 못한 항목은 통과 처리하지 않는다.

**P0:** 신청·마감·발표·본인 정보·중복 방지 등 배포 전 필수. **P1:** 입력 경계값, 복구, 다양한 화면·데이터 조합.

## 6. 시간·캐시 확인

| ID | 우선 | 실행 방법 | 기대 결과 | 결과 |
| --- | --- | --- | --- | --- |
| T01 | P0 | 메인 발표 카운트다운과 현재 회차 접수 여부를 `GET /api/v1/match/summary`와 대조 | 요청마다 새로 계산된 `serverNow`와 수신 후 경과 시간 기준. `timetable.serverNow`를 기준으로 삼지 않음 | — |
| T02 | P0 | 기기 시계를 실제보다 빠르게/느리게 설정한 뒤 페이지 재진입. 이후 다른 탭에서 복귀 | 서버 시각을 다시 받은 후 발표 카운트다운·신청 가능 여부가 같은 서버 상태를 따름. 음수 카운트다운 없음 | — |
| T03 | P0 | 카운트다운이 0이 되어도 서버는 CLOSED로 유지. 이후 OWNER 발표하고 재조회 | 예정 시각 도착과 실제 발표를 구분. 실제 발표 전에는 상대 정보 미공개 | — |
| T04 | P1 | 운영자가 회차·공연 시각을 수정한 뒤 사용자 화면 재조회. 창을 계속 열어 둔 경우도 별도 관찰 | 다음 조회에서 갱신된 데이터 반영. 서버 캐시 갱신과 브라우저 자동 갱신을 구분하여 소요 시간 기록 | — |

메인·프로필·신청·결과 화면은 쿠키를 포함한 SSE 연결을 공유한다. `connected` 직후 요약을 조회하고, `round-opened`·`round-closed`·`round-published` 수신 후 0~3초 무작위 지연을 두어 다시 조회한다. 발표 이벤트와 재연결에서는 결과도 확인한다. 탭 복귀 시 즉시 갱신하며 서버 기준 타이머가 0이면 조회하고 상태가 그대로일 때 5초마다 다시 확인한다. 신청 가능 여부는 시각이 아닌 `currentRound.status === OPEN`을 따른다. 기기 시각 변경으로 경과 시간이 튀지 않도록 `performance.now()`를 사용한다.

일반 SSE 끊김은 브라우저의 재연결에 맡긴다. 네이티브 `EventSource` 오류에는 HTTP 상태가 없어 연결이 완전히 닫혔을 때만 같은 주소의 응답 헤더를 확인하고 스트림을 즉시 중단한다. 이 확인 요청에서 HTTP 503인 경우에만 30초 폴링으로 전환하며 정상 `connected` 수신 시 폴링을 종료한다. 다른 HTTP 오류·네트워크 오류를 503으로 취급하지 않는다. 로그인·로그아웃 시 연결을 교체하고 관련 화면을 떠나면 닫는다. `/auth/me`는 최초 인증 확인과 명시적인 인증 재시도에만 호출한다.

추가 확인 항목:
- 정상 연결 상태로 60초 대기해 요약·`/auth/me`의 30초 반복 호출이 없는지 확인한다. 예정된 마감 시각과 겹치지 않게 준비한다.
- 각 회차 이벤트 뒤 0~3초 안에 재조회하고, 발표 시 결과 화면까지 갱신되는지 확인한다. 이벤트 본문은 상태 판정에 사용하지 않는다.
- 서버 상태를 예정 시각이 지난 OPEN으로 유지하면 신청이 가능하고, CLOSED로 변경되면 수정·취소 버튼이 사라지는지 확인한다.
- SSE 503만 30초 폴링으로 전환되는지, 정상 복구·로그아웃·다른 화면 이동 후 이전 연결과 타이머가 남지 않는지 확인한다.
- 응원 등록 응답을 2초 지연해 버튼의 로딩 표시와 비활성화를 확인한다. 연속 클릭·Enter로 POST가 중복 발생하지 않아야 한다.
- 미매칭 결과에서 다음 회차 자동 이월 안내와 서버의 실제 신청 상태를 대조한다.

타임테이블은 별도로 약 60초마다 조회한다. 운영자 수정에 따른 서버 캐시 갱신과 브라우저 재조회 시점을 구분한다.

타임테이블 응답의 시각·LIVE 상태는 안내된 캐시 지연을 허용하되, 인스타팅 신청/마감 판정의 시계로 사용해서는 안 된다. 랜딩의 축제 시작 타이머는 별도 기능이며 이번 인스타팅 발표 카운트다운과 구분한다.

## 8. 완료 기준과 버그 기록

**QA 완료 기준:** P0 항목 모두 통과, 신청 중복·타인 정보 노출·마감 후 저장·발표 전 공개 없음, 성공/미매칭/이월/재참여/신고 결과를 서버 상태와 대조 완료. 보류 항목과 미실행 브라우저는 따로 남긴다.

시간이 부족한 1차 점검에서는 A01~A08 → B01~B03 → C02~C07 → D01·D04~D06·D08 → R01·R03·R04 → E01·E03 → T01·T03을 먼저 실행한다. 이후 나머지를 완료하며, 1차 점검만으로 전체 QA 통과로 표시하지 않는다.

버그마다 다음 내용을 남긴다.

```text
제목: [인스타팅][케이스 ID] 실제로 발생한 문제
환경: 프론트 주소 / 배포 버전 / 브라우저·기기 / 발생 시각(KST)
계정·회차: 테스트 계정 별칭 / USER·STAFF·OWNER / roundSeq·roundId / 회차 상태
재현: 1) ... 2) ... 3) ...
기대 결과:
실제 결과:
증거: 화면 캡처 / 요청 경로·메서드 / HTTP 상태·오류 코드
저장 상태: 내 신청·결과 재조회로 확인한 실제 서버 상태
반복 여부: 항상 / 간헐 / 한 번
```

쿠키·인증 토큰과 실사용자의 인스타 ID는 버그 첨부 자료에서 가린다. 테스트가 끝나면 회차·신청·신고·제재 등 변경한 테스트 데이터를 정리하고, 다음 실행에 필요한 초기 상태를 복원한다.
