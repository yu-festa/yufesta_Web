# 새 공지 알림 운영 설정

인스타팅 신청 완료 화면과 마이페이지에서 **공지 알림 받기**를 누르고 브라우저 권한을 허용한 기기에, 신청 이후 등록된 모든 새 공지를 발송합니다. 회차·제목·긴급 배너 여부로 구분하지 않습니다. 알림에는 제목과 본문 요약이 표시되며 누르면 `/main#notices/{id}`로 이동합니다.

기존 랜딩 오픈 알림 화면, 예약 API, 발송 시각은 그대로입니다. VAPID 키와 QStash 계정만 공유하며 기존 랜딩 신청자를 공지 구독자로 자동 전환하지 않습니다. 공지 알림 해제도 랜딩 예약이나 브라우저 전체 푸시 구독을 취소하지 않습니다.

## 사용자가 진행할 설정

### 1. 무료 Redis 저장소 생성

1. [Upstash Console](https://console.upstash.com/)에서 Redis 데이터베이스를 **Free** 플랜으로 하나 생성합니다. 이미 Free 데이터베이스를 쓰고 있다면 기존 저장소를 공유할 수 있습니다. 공지 데이터는 사이트별 별도 키 공간에 저장됩니다.
2. 데이터베이스의 `REST URL`과 쓰기 가능한 `REST Token`을 확인합니다. Read Only Token은 사용할 수 없습니다.
3. 토큰은 채팅·Git에 올리지 말고 Vercel 환경변수에 직접 입력합니다. 무료 이용이 목적이면 Pay as You Go로 전환하지 않습니다.

### 2. Vercel Production 환경변수 설정 후 배포

| 이름 | 값 |
| --- | --- |
| `NOTICE_PUSH_ENABLED` | `true` |
| `NOTICE_API_ORIGIN` | `https://api.yufesta.com` |
| `UPSTASH_REDIS_REST_URL` | Redis의 REST URL |
| `UPSTASH_REDIS_REST_TOKEN` | Redis의 REST Token |
| `PUSH_PUBLIC_ORIGIN` | 실제 대표 도메인. 예: `https://yufesta.com` |

기존 `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `QSTASH_CURRENT_SIGNING_KEY`, `QSTASH_NEXT_SIGNING_KEY`를 그대로 유지합니다. `QSTASH_TOKEN`은 기존 랜딩 예약과 아래 자동 설정 명령에 필요합니다. `PUSH_OPEN_AT`과 `PUSH_OPEN_MODE`는 변경하지 않습니다. 모두 서버 변수이며 `VITE_` 접두사를 붙이지 않습니다.

이 코드가 포함된 Production 배포를 생성합니다. 환경변수만 바꾸면 기존 배포에는 적용되지 않습니다. Preview 배포는 `NOTICE_PUSH_ENABLED`를 끄고 운영용 Redis에 연결하지 않습니다. 설정이 준비되기 전에는 신청 버튼에 준비 안내가 표시되며 성공으로 표시되지 않습니다.

### 3. QStash 스케줄 하나 등록

QStash Console의 Schedules에서 다음 값으로 **한 개만** 만듭니다.

| 항목 | 값 |
| --- | --- |
| Destination URL | `https://yufesta.com/api/notice-notification-poll` — 대표 도메인에 맞춤 |
| Method | `POST` |
| Cron | `*/5 * * * *` (5분마다) |
| Content-Type | `application/json` |
| Body | `{}` |
| Retries | `1` |

Vercel Cron은 추가하지 않습니다. 콜백 URL은 외부에서 리다이렉트나 배포 보호 화면 없이 접근할 수 있어야 합니다. 직접 브라우저로 호출하면 메서드/서명 검증 때문에 실패하는 것이 정상입니다. QStash가 보낸 요청만 실행합니다.

콘솔 대신 자동 등록하려면 `.env.local`에 위 서버 변수와 기존 QStash/VAPID 변수를 넣고 `npm run setup:notice-push`를 실행할 수 있습니다. 이 명령은 배포된 공개키 및 Redis 연결을 확인한 뒤 고정 ID로 스케줄을 생성하거나 갱신합니다. 실제 QStash 설정을 변경하는 명령이며, 테스트에서는 실행하지 않습니다. 콘솔 방식과 명령 방식 중 하나만 사용해 중복 스케줄을 만들지 마세요.

### 4. 실제 기기 확인

1. QStash의 첫 스케줄 실행이 200으로 성공하는지 확인합니다. 처음 실행하면 기존 공지를 기준으로 저장하며 과거 공지를 보내지 않습니다.
2. 사이트를 새로고침해 최신 서비스 워커를 적용합니다. iPhone/iPad는 홈 화면에 추가한 앱에서 실행합니다.
3. 인스타팅 신청 완료 화면 또는 마이페이지에서 **공지 알림 받기**를 누르고 권한을 허용합니다. **공지 알림을 받고 있어요**가 표시되는지 확인합니다.
4. 관리자 화면에서 **새 공지 한 건**을 등록합니다. 제목만 수정하는 것은 새 공지가 아닙니다. 테스트 공지도 실제 구독자 모두에게 전달되므로 운영 공지 또는 별도 테스트 환경을 사용합니다.
5. 사이트를 닫아도 다음 5분 확인 이후 알림이 도착하는지, 클릭하면 해당 공지로 이동하는지 확인합니다. 기기·브라우저·네트워크 사정에 따른 추가 지연은 가능합니다.
6. 마이페이지에서 공지 알림을 해제한 기기는 이후 새 공지를 받지 않는지 확인합니다. 해제 직전에 이미 전송된 알림은 도착할 수 있습니다.

## 비용과 사용량 (2026-09-28 공식 요금표 확인)

- **QStash Free:** 하루 1,000회 전달 시도. 재시도도 1회로 계산하며 예약 스케줄 실행마다 계산합니다. [공식 요금표](https://upstash.com/pricing/qstash)
- 이 구조는 사용자마다 QStash 작업을 만들지 않습니다. 하루 기본 **24 × 60 ÷ 5 = 288회**입니다. Vercel이 Web Push를 직접 보내므로 200명에게 공지를 보내도 그 200회는 QStash 메시지에 추가되지 않습니다.
- 예: 정상 확인 288회 + 기존 랜딩 오픈 알림 200건 = **488회/일**. 모든 확인이 한 번씩 재시도되면 확인만 576회이며, 여기에 다른 작업과 재시도를 합산합니다. 같은 계정의 기존 사용량은 별도 확인해야 합니다.
- **Redis Free:** 월 500,000 명령, 저장 256MB, 전송 10GB, Free 데이터베이스 1개. [공식 요금표](https://upstash.com/pricing/redis)
- 새 공지가 없는 확인은 Redis 명령 3회(잠금·상태 조회·잠금 해제), 한 달 30일 약 **25,920회**입니다. 공지 1건을 200명에게 성공적으로 보내면 발송 전 구독 확인·발송 기록 저장으로 약 400회와 공통 처리 몇 회가 추가됩니다. 하루 공지 10개라면 한 달 대략 15만~20만 명령 수준이며, 재시도·신청·상태 조회는 추가됩니다.
- 따라서 **구독자 100~200명, 하루 공지 약 10건, 정상 운영 기준으로 QStash와 Redis 무료 한도 안에서 처리 가능**합니다. 가입자 수만으로 무료를 보장하는 것은 아니며, 실제 공지 수·장애 재시도·다른 기능 사용량을 합산해야 합니다. Vercel 함수·트래픽 사용량은 Vercel 요금제에서 별도로 확인합니다.

## 구현과 제한

- `GET /api/notice-notification`: 공개키만 반환. `POST`의 `subscribe`, `status`, `unsubscribe`는 해당 브라우저 구독을 등록·확인·해제합니다. 로그인 계정이 아닌 기기 단위이며 신청 취소/로그아웃으로 자동 해제되지 않습니다. 알림 해제 버튼으로 별도 해제합니다.
- 신청 경로는 완료 화면과 마이페이지입니다. 공개 축제 공지를 구독하는 API로, 서버가 인스타팅 참가 자격을 별도로 인증하는 기능은 아닙니다.
- `POST /api/notice-notification-poll`: QStash 서명과 목적지를 검증하고 공지를 한 번 조회합니다. 변화가 없으면 구독자 전체를 읽지 않습니다.
- 구독 주소·키·시작 기준은 VAPID 비밀키에서 별도 도출한 AES-GCM 키로 암호화해 Redis에 저장합니다. 운영 중 VAPID 비밀키를 바꾸면 기존 구독 정보의 복호화가 불가능합니다.
- 최초 기준 목록 및 신청 전 생성된 공지는 제외합니다. 새 ID의 공지는 종류와 관계없이 발송하며, 기존 ID의 수정은 재발송하지 않습니다. 시간대 없는 서버 날짜는 한국 시간으로 해석합니다.
- 먼저 발송 대기를 영속 저장하고 기기별 완료 기록을 남깁니다. 일시 실패는 다음 확인에서 실패한 기기만 재시도하며, 404/410 기기는 제거합니다. 발송 대기는 최초 감지 후 최대 7일, 완료 기록은 8일 유지합니다. 기기로 전송된 푸시는 최대 24시간 전달을 기다립니다.
- 10개 기기씩 병렬 처리하며 시간 예산을 넘는 나머지는 다음 확인으로 넘깁니다. 대량 공지·연결 장애 때는 5분보다 더 지연될 수 있습니다.
- 푸시 서비스가 수락한 직후 Redis 기록 전에 함수가 종료되는 경우처럼 외부 서비스 사이에서 **중복을 완전히 보장할 수 없는 구간**이 있습니다. 공지별 동일 알림 태그를 사용해 동일 공지의 알림이 쌓이는 것을 줄입니다. 서비스 수락은 기기의 실제 표시를 보장하지 않습니다.
- 현재 공지 GET API는 최신 50건만 반환합니다. 확인 사이 또는 장애 기간에 50건을 초과해 등록되거나, 조회 전에 삭제된 공지는 놓칠 수 있습니다. 그 규모까지 빠짐없이 보장하려면 백엔드의 페이지 조회/공지 등록 이벤트가 필요합니다. 한 번 감지한 공지는 Redis에 보관되므로 이후 목록에서 밀려나도 재시도됩니다.
- 작업 응답의 `possibleGap: true`는 최신 50건과 기존 ID가 겹치지 않아 누락 가능성이 있음을 뜻합니다. `failed`, `pending`, `expired`는 각각 이번 실패·다음 확인 대기·7일 만료 공지 수를 확인하는 데 사용합니다. 구독 원문이나 키는 로그에 남기지 않습니다.
- 종료 시 QStash 스케줄을 Pause/Delete하고 `NOTICE_PUSH_ENABLED=false`로 재배포합니다. 이 설정은 랜딩 예약에 영향을 주지 않습니다. 구독자 및 발송 대기 데이터는 자동 전체 삭제하지 않으며, 축제 종료 후 필요에 따라 해당 사이트의 Redis 키 공간을 정리합니다.

## 검증

`npm run test:push`로 기존 랜딩 예약, 서명/암호화, 새 공지 감지, 부분 실패 재시도, 해제/만료 구독, 시간 예산, 공지 상세 이동 및 서버 배포 빌드를 검사합니다. 실제 QStash·Redis 계정에 연결하거나 실제 사용자에게 알림을 보내는 테스트는 아닙니다. 운영 검증은 위 4단계로 별도 수행합니다.
